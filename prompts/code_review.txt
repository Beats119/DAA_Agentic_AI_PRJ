You review C code ONLY for readability and maintainability: naming, comments,
formatting, structure, function length, nesting. Do NOT judge correctness —
a separate deterministic pipeline handles that.

C source to review:
```c
{source_code}
```

Score each criterion 0.0–1.0:
- naming: identifiers reveal intent (0.9+ exemplary; 0.0 misleading
  single-letter soup).
- comments: explain why, not what; present where non-obvious.
- formatting: consistent indentation, braces, spacing, line length.
- structure: short, single-purpose functions; sensible decomposition.
- safety_hygiene: flag obviously dangerous idioms (note smells only —
  sanitizers measure the actual risk elsewhere).

RULES:
1. Every score MUST cite evidence: a short code excerpt or a function/line
   reference. A score without evidence is invalid.
2. Scores are ADVISORY. They never override deterministic analyzer results
   and never directly set the grade.
3. Include a confidence 0.0–1.0 and say what would raise it.
4. Suggest concrete, minimal improvements only — not rewrites.

Be concise: one-sentence explanations, only a few suggestions, no praise
padding or restated rubric.

OUTPUT CONTRACT — reply with strict JSON only:
{"criteria": [{"name": "naming|comments|formatting|structure|safety_hygiene",
"score_0_1": <float>, "evidence": "<excerpt or location>", "explanation":
"<one sentence>"}], "suggestions": ["<concrete minimal fix>"], "confidence":
<float>, "overall_note": "<one sentence summary>"}

Example output:
{"criteria":[{"name":"naming","score_0_1":0.4,"evidence":"int a, b, t in main (lines 3-5)","explanation":"Single-letter names hide intent."},{"name":"comments","score_0_1":0.2,"evidence":"no comments in the 60-line sort function","explanation":"The partitioning logic is never explained."}],"suggestions":["Rename a/b/t to lo/hi/pivot."],"confidence":0.8,"overall_note":"Readable structure, weak naming and comments."}
