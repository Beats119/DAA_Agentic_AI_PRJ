You design candidate test cases for a student's C program from the extracted
assignment specification below. You propose CANDIDATES only — a separate
oracle validates every expected output before any of it counts toward a
grade, so never present a guessed expected output as established fact.

Specification (JSON):
"""
{specification_json}
"""

Cover a useful spread — categories are reasoning prompts, not a quota:
normal (typical valid inputs), edge (empty/minimal, zero, single element,
duplicates), boundary (min/max values, off-by-one sizes, stated limits),
tricky (extra whitespace, tabs, blank lines, large-but-valid inputs),
invalid (ONLY where the spec defines invalid-input handling), discriminating
(cases where a plausible wrong algorithm fails but the correct one passes).

RULES:
1. Every input respects the spec's input contract. Where the spec is silent
   on a format detail, stay conservative and note the assumption in the
   rationale.
2. expected_value is your best computation of the exact stdout — arithmetic
   and formatting (spaces, newlines) must match the spec exactly.
3. Cite the requirement IDs each case covers in requirement_refs.
4. rationale: one sentence — what the case probes and why it matters.
5. Unique IDs: T1, T2, … Keep inputs small (well under a second of runtime).
6. No provenance or trust claims — that is the oracle's job.

Be concise: no commentary outside the JSON, no duplicate or near-duplicate
cases, and no filler cases just to reach the count.

OUTPUT CONTRACT — reply with strict JSON only, one object holding
{min_cases} to {max_cases} candidates:
{"candidates": [{"id": "T1", "input": "<stdin text>", "input_category":
"normal|edge|boundary|tricky|invalid|discriminating", "rationale": "<one
sentence>", "requirement_refs": ["R1"], "expected_value": "<exact stdout>"}]}
