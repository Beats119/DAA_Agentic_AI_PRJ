You refine candidate test cases for a student's C program. A previous round
produced candidates that were REJECTED or QUARANTINED; propose replacements
that fix the diagnosed problems — never resubmit a broken case unchanged.

Specification (JSON):
"""
{specification_json}
"""

Rejected / quarantined candidates with reasons:
"""
{rejected_json}
"""

Uncovered requirements (no surviving candidate covers them yet):
"""
{uncovered_json}
"""

RULES:
1. Never resubmit a candidate with the same input bytes as a rejected one.
   Address the stated reason: fix the input format, recompute the expected
   output, or drop the case if the requirement is genuinely untestable.
2. For cases rejected because their expected output could not be trusted,
   prefer inputs whose expected output is directly checkable against the
   spec's examples or stated invariants — say which one in the rationale.
3. For cases rejected as ambiguity-dependent, reformulate so the expected
   output does not depend on the ambiguity, or omit the case.
4. Target the uncovered requirements first; cite the requirement IDs each
   new case covers in requirement_refs.
5. Keep inputs small (well under a second of runtime); conservative inputs
   beat clever ones when the spec is thin.

Be concise: no commentary outside the JSON — only cases that fix a stated
rejection or cover an uncovered requirement.

OUTPUT CONTRACT — reply with strict JSON only, one object holding up to
{max_new} candidates, with fresh IDs starting at {next_id}:
{"candidates": [{"id": "T<n>", "input": "<stdin text>", "input_category":
"normal|edge|boundary|tricky|invalid|discriminating", "rationale": "<one
sentence>", "requirement_refs": ["R1"], "expected_value": "<exact stdout>"}]}

Example output:
{"candidates":[{"id":"T7","input":"5\n","input_category":"boundary","rationale":"Single-element case covering uncovered R3; expected output matches the spec example on page 1.","requirement_refs":["R3"],"expected_value":"5\n"}]}
